==================================================
檔案用途
==================================================

檔案：

firestore.rules

用途：

Firebase Firestore 安全性規則檔。

此檔案是整個系統最重要的資安防線。

前面分析的：

- admin.js
- article.js
- blog.js

都只是前端程式。

真正能不能：

新增文章
修改文章
刪除文章
核准留言
刪除留言

不是由 JavaScript 決定。

而是由 firestore.rules 決定。

==================================================

==================================================

目前資料庫共有兩個 Collection：

articles
comments

潛在問題
==================================================

中風險

request.auth != null

代表：

任何 Firebase 登入帳號

都能看草稿。

==================================================

例如：

user@gmail.com

只要存在 Firebase Auth

即可存取。

==================================================

理想做法

Admin Claim

範例：

allow read:
if resource.data.published == true
|| request.auth.token.admin == true;

第11行
==================================================

原始碼：

allow write:
if request.auth != null;

==================================================
作用
==================================================

允許：

create
update
delete

全部寫入操作。

==================================================
重大安全風險
==================================================

高風險

目前：

任何登入 Firebase 的帳號

皆可：

新增文章

修改文章

刪除文章

發布文章

下架文章

==================================================

例如：

使用者註冊：

abc@gmail.com

↓

Firebase Auth 帳號建立

↓

直接取得文章寫入權限

==================================================

如果系統未限制 Auth 建立方式

非常危險。

==================================================
企業最佳做法
==================================================

使用 Custom Claims。

範例：

allow write:
if request.auth.token.admin == true;

--------------------------------------------------

或

allow write:
if request.auth.uid ==
"xxxxx_admin_uid";

==================================================

原始碼：

if request.resource.data.approved == false

作用

--------------------------------------------------

拒絕：

==================================================

與規則一致。

==================================================

==================================================

原始碼：

作用：

強制作者名稱必須字串。

==================================================
作者長度限制
==================================================

原始碼：

author.size() > 0
author.size() <= 50

作用：

避免：

空字串

過長字串

==================================================
留言驗證
==================================================

原始碼：

message.size() <= 1000

作用：

限制留言長度。

==================================================
優點
==================================================

避免：

超大文件寫入。

--------------------------------------------------

降低：

Firestore 費用

Storage 成本

DoS 風險

==================================================
隱藏風險
==================================================

目前未驗證：

articleId

是否存在。

==================================================

因此可發生：

comments

articleId = "abcxyz"

但：

articles/abcxyz

不存在。

==================================================

產生：

孤兒留言

(orphan comment)

==================================================
建議改善
==================================================

allow create:

加入：

exists(
/databases/$(database)/documents/articles/
$(request.resource.data.articleId)
)

==================================================
更大風險
==================================================

目前未限制欄位。

使用者可寫：

{
 approved:false,
 author:"abc",
 message:"test",

 hacking:true,
 admin:true,
 role:"root",
 secret:"xxx"
}

==================================================

雖然系統目前沒使用。

但資料庫會被污染。

==================================================
企業做法
==================================================

限制欄位。

例如：

request.resource.data.keys().hasOnly([
"articleId",
"author",
"message",
"approved",
"spam",
"createdAt"
])

==================================================
最終結論
==================================================

此 firestore.rules 的整體設計方向正確：

訪客只能看已發布文章與已核准留言，
留言必須先審核，
後台需登入才能操作。

但最大的資安漏洞是：

任何 Firebase 已登入帳號都具有管理員權限。

若要正式上線，第一優先應改成：

request.auth.token.admin == true

並搭配 Firebase Custom Claims 管理角色權限。
